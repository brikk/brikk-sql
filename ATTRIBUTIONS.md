## sqlglot

`brikk-sql` is a Kotlin port of [sqlglot](https://github.com/tobymao/sqlglot) by Toby Mao
and contributors, licensed under the MIT License. The port covers the tokenizer, parser,
AST node catalog, SQL generator, and dialect implementations, and is pinned to upstream
version `v30.18.0-43-g3ca82489`. Test fixtures under `brikk-sql/testResources/`
(identity/dialect/serde corpora) are derived from sqlglot's MIT-licensed test suite.

Ported code carries `// sqlglot: <symbol>` provenance comments referencing the Python
counterparts. Generated files (token tables, AST catalog, function registries) are
produced by the scripts in `tools/` from the pinned upstream source.

## Apache Doris

Doris-derived artifacts are included from https://github.com/apache/doris and
https://github.com/apache/doris-website, both Apache License 2.0:

- `vendor/lib/doris-fe-sql-parser-*.jar` — a locally-built snapshot of Doris's standalone
  `fe-sql-parser` module (pre-release; see vendor/README.md for provenance and refresh
  procedure). The current artifact combines the exact 4.1.5 release grammar with
  the upstream standalone parser facade; both source pins are in `vendor/README.md`.
- `brikk-sql-metadata/.../GeneratedDorisFunctionCatalog.kt` — function names/aliases/kinds
  extracted from Doris's runtime function registry
  (`fe/fe-core/.../catalog/Builtin*Functions.java`) by `tools/generate_doris_functions.py`
  (adapted from the doris-intellij-plugin extraction script), at tag `4.1.5-release`.
- `vendor/data/doris-since-versions.json` — per-function "first documented in" version,
  extracted from `apache/doris-website`'s function docs
  (`docs/sql-manual/sql-functions/`, `versioned_docs/version-*/sql-manual/sql-functions/`)
  by `tools/extract_doris_since_versions.py`; joined onto `FunctionDef.firstDocumentedIn`. See
  vendor/README.md for the extraction method and its honesty caveats.
- `vendor/data/doris-keywords-4.1.5.tsv` and `GeneratedKeywords.kt` — keyword spellings,
  token symbols and reservation read from the vendored 4.1.5 parser's grammar.

## Trino

spellings and reservation read from the trino-grammar 484 lexer and parser. Historical
483 captures remain available under `vendor/data/`. Trino is
licensed under the Apache License 2.0. No Trino code is included — only registry and
grammar data.

## ClickHouse

`vendor/data/clickhouse-functions-26.5.1.1.tsv` and the generated
`brikk-sql-metadata/.../GeneratedClickhouseFunctionCatalog.kt` contain ClickHouse
26.5.1.1 function names, aggregate kinds, and evidence-backed aliases extracted from
`system.functions`; `vendor/data/clickhouse-keywords-26.5.1.1.tsv` and
`GeneratedKeywords.kt` hold its `system.keywords`. No ClickHouse source code is included in the catalog artifact.
ClickHouse is licensed under the Apache License 2.0; see vendor/README.md for provenance.

`vendor/data/clickhouse-2026-audit/` includes native formatter output and finite-query
results from official ClickHouse 26.8.34.13 LTS and 26.10.2.103 stable builds. STREAM
grammar handling follows the pinned Apache-2.0 upstream parser; source links and
immutable engine digests are recorded with the fixtures. Brikk's AST observations
and regression cases are separate from the historical function catalog.

The official-build registry, type, settings, build-option and embedded-documentation
captures `vendor/data/clickhouse-*-26.8.34.13.*` and `clickhouse-*-26.10.2.103.*`
and their generated Kotlin metadata also derive from those Apache-2.0 ClickHouse
builds. Capture manifests retain the exact image digests, queries and SHA-256 hashes.
No documentation prose is treated as a machine-readable function signature.

The ClickHouse batch-3 parser/analyzer corrections and audit fixtures reference the
same Apache-2.0 upstream's v26.10.2.103-stable parser and function-composition source.
The fixture file records the source URLs; native observations retain the image
digests. No source statement from the DDL fixtures is executed by the verifier.

The final batch-4 behavior captures and regression reruns use those same immutable
Apache-2.0 ClickHouse images. The PostgreSQL cardinality source contract is cited
from the PostgreSQL array-functions documentation, separately from the native
ClickHouse target results; this is not a live PostgreSQL equivalence capture.

`vendor/data/clickhouse-semantic/` retains formatter output and finite-query
results from those same Apache-2.0 builds for CHSEM-001. The fixture links the
official composition announcement and tagged analyzer source; its guide records
the authored controls, exact engine digests and result/error evidence. This adds
no ClickHouse source code to the published library and claims no overload catalog.

The CHSEM-002 `callable-sources.json` in that directory includes selected
Apache-2.0 C++ declaration excerpts from the exact same release tags, with original
paths, line ranges and whole-file hashes. `tools/capture_clickhouse_callable_sources.py`
reproduces them. The internal Kotlin callable-fact descriptions follow those
declarations, with native argument/type observations recorded separately. The
excerpts are research evidence, not source bundled into the published library.

CHSEM-003's `lambda-input-native/` captures in the same directory contain additional
finite argument-type and error observations from the same pinned Apache-2.0 images.
They remain separate from the earlier callable and historical semantic captures.

CHSEM-004's `composition-native/` captures add original-query result/error evidence
from the same pinned Apache-2.0 builds. The internal rule checker follows the tagged
composition and callable declarations already cited in that directory; it does not
replace historical evidence or claim native whole-query/execution equivalence.

CHSEM-005's `result-native/` and `result-matrix/` captures add original return-type
observations from the same Apache-2.0 images. Primitive multiplication result typing
follows the tagged `NumberTraits::ResultOfAdditionMultiplication` declaration already
cited in `callable-sources.json`; the complete pair matrix is independently observed
from the engines rather than generated from that formula.

CHSEM-007's `qualification-native/` captures add finite original/generated
execution and parser observations from the same exact Apache-2.0 ClickHouse images.
Earlier raw captures are preserved separately.

CHSEM-008's `higher-order-sources.json` includes Apache-2.0 implementation excerpts
for array predicate/sort contracts, tuple binding, mapApply adapters and comparison
return types. `higher-order-native/` records original/generated witnesses from the
same exact Apache-2.0 ClickHouse images, separately from older evidence.

CHSEM-009's `overload-sources.json` adds Apache-2.0 excerpts for FieldToDataType,
getLeastSupertype, DecimalUtils and default NULL return typing. `overload-native/`
and `literal-types/` retain independent original/generated and integer-boundary
observations from the same exact Apache-2.0 images. Earlier captures remain intact.

## Apache DataFusion (sqllogictest parse corpus)

`brikk-sql/testResources/dialect-corpus/datafusion-slt-parse.json` is extracted by
`tools/extract_datafusion_slt_corpus.py` from a curated subset of
[Apache DataFusion](https://github.com/apache/datafusion)'s own sqllogictest suite
(`datafusion/sqllogictest/test_files/*.slt`). It contains only SQL statement text (no
DataFusion code) used as a real-engine parse-acceptance backstop for brikk's `datafusion`
dialect. DataFusion is licensed under the Apache License 2.0.

## GoogleSQL pipe syntax

The pipe-syntax (`|>`) operator semantics implemented in `brikk-sql` (first-class
`PipeQuery`/stage nodes, desugaring behavior, operator set) follow the
[GoogleSQL pipe query syntax](https://cloud.google.com/bigquery/docs/reference/standard-sql/pipe-syntax)
specification published by Google (Apache 2.0-licensed documentation in the
googlesql/ZetaSQL project). No code from ZetaSQL is included.
